# MCP InSales Project Rules & Architecture
## Overview
Development of an MCP server to integrate AI agents with the InSales e-commerce platform via REST API.

## Core Technologies
- Language: Go (>=1.24)
- Protocol: Model Context Protocol (MCP)
- Database: PostgreSQL (for user/key management)
- Deployment: Docker (multi-stage, optimized for low-resource VPS)

## Architecture Principles
1. **Clean Architecture**: Separation of concerns between Domain logic, Use Cases, Infrastructure, and the MCP Layer.
2. **Dependency Injection**: All dependencies (DB, InSales Client, Logger) must be injected via constructors.
3. **Mapper Pattern**: Map InSales API responses to internal models immediately; never leak raw API structures into business logic or the MCP layer.
4. **Multi-tenancy**: Use a context-aware system where each request is tied to a unique user ID and their specific InSales credentials retrieved from the database.

## Coding Standards (Go)
- **Idiomatic Go**: Follow "Effective Go" standards.
- **Error Handling**: Wrap errors with context; never ignore them.
- **Concurrency**: Use goroutines/channels only when necessary, always managed by `context.Context`.
- **Logging**: Structured logging (slog or similar).

## Implementation Guidelines for OpenCode
1. **Infrastructure First**: Establish the database schema and core configuration before building features.
2. **Service Isolation**: 
   - `internal/integration/insales`: Pure client logic with retry policies and rate limiting.
   - `internal/mcp`: Mapping of MCP tools to internal service calls.
3. **Optimization**: Focus on memory efficiency and minimal resource consumption for VPS deployment. Use static linking (CGO_ENABLED=0).

## Security Requirements
1. No hardcoded secrets; use .env files and DB storage for InSales keys.
2. JWT or API Keys for internal auth to the MCP server.
3. Rate limiting at the application level.
