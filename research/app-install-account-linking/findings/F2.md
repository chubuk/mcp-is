# F2: Passwordless-механизмы привязки аккаунта (magic link, OTP на e-mail, passkeys) — задокументированные link-identity flows у Auth0, Clerk, Supabase, Firebase, WorkOS при совпадении e-mail: link vs merge vs block.

## Findings

### [1] Supabase Auth по умолчанию автоматически мерджит (auto-link) новые OAuth-идентичности в существующего пользователя с тем же e-mail — это явная задокументированная политика link+merge.
- quote: "Supabase Auth automatically links identities with the same email address to a single user... When a new user signs in with OAuth, Supabase Auth will attempt to look for an existing user that uses the same email address. If a match is found, the new identity is linked to the user."
- url: https://supabase.com/docs/guides/auth/auth-identity-linking
- source_type: primary
- published: unknown (fetched 2026-10-29)
- confidence: high

### [2] Supabase привязывает автоматически только к уникальным и верифицированным e-mail и снимает все неподтверждённые идентичности при линке — явная защита от pre-account takeover.
- quote: "It would also be an insecure practice to automatically link an identity to a user with an unverified email address since that could lead to pre-account takeover attacks. To prevent this from happening, when a new identity can be linked to an existing user, Supabase Auth will remove any other unconfirmed identities linked to an existing user."
- url: https://supabase.com/docs/guides/auth/auth-identity-linking
- source_type: primary
- published: unknown (fetched 2026-10-29)
- confidence: high

### [3] Supabase блокирует создание второго аккаунта с e-mail, уже занятым OAuth-идентичностью: отвечает обфусцированным ответом без письма верификации (анти-enumeration), т.е. коллизия e-mail = block, не merge.
- quote: "If you try to create an email account after previously signing up with OAuth using the same email, you'll receive an obfuscated user response with no verification email sent. This prevents user enumeration attacks."
- url: https://supabase.com/docs/guides/auth/auth-identity-linking
- source_type: primary
- published: unknown (fetched 2026-10-29)
- confidence: high

### [4] Clerk автоматически линкует OAuth-аккаунт к существующему аккаунту с тем же e-mail при верифицированном e-mail с обеих сторон, и OAuth-линк обходит проверку пароля даже для password-защищённых аккаунтов.
- quote: "When a user signs in to your app using an OAuth provider that returns a verified email address, Clerk links the OAuth account to the existing account and signs the user in. This even applies to password-protected accounts, as the OAuth sign-in process automatically bypasses password verification."
- url: https://clerk.com/docs/guides/configure/auth-strategies/social-connections/account-linking
- source_type: primary
- published: 2026-10-27 (lastUpdated на странице)
- confidence: high

### [5] Clerk не линкует без завершённой верификации e-mail: неверифицированный e-mail у OAuth → сначала verification flow; неверифицированный e-mail у существующего Clerk-аккаунта → принудительная смена пароля и доп. проверки перед линком (анти-takeover).
- quote: "if an account was created with an unverified email/password combination and the user later signs in with Google (where the email is verified), Clerk will prompt the user to change their password before linking the accounts. This process begins with email verification, regardless of the method used."
- url: https://clerk.com/docs/guides/configure/auth-strategies/social-connections/account-linking
- source_type: primary
- published: 2026-10-27 (lastUpdated на странице)
- confidence: high

### [6] Clerk при разных e-mail у аккаунтов не автоматизирует линк: пользователь вручную добавляет второй e-mail через компонент <UserProfile />, после чего OAuth-аккаунты обоих адресов линкуются к одному пользователю.
- quote: "If a user has a different email from the one associated with the OAuth account, they can manually associate the two by following these steps: 1. Sign in to their Clerk application with the account that uses their main email address. 2. In the <UserProfile />, add the different email."
- url: https://clerk.com/docs/guides/configure/auth-strategies/social-connections/account-linking
- source_type: primary
- published: 2026-10-27 (lastUpdated на странице)
- confidence: high

### [7] Firebase при настройке "One account per email address" при совпадении e-mail с другим провайдером кидает auth/account-exists-with-different-credential и документирует link-flow только после proof-of-control: сначала войти через существующий провайдер, затем linkWithCredential(pending) — авто-мерджа нет.
- quote: "when a user tries to sign in a to a provider (such as Google) with an email that already exists for another Firebase user's provider (such as Facebook), the error auth/account-exists-with-different-credential is thrown along with an AuthCredential object... To complete the sign in to the intended provider, the user has to sign first to the existing provider (Facebook) and then link to the former AuthCredential (Google ID token)."
- url: https://firebase.google.com/docs/auth/web/google-signin
- source_type: primary
- published: unknown (fetched 2026-10-29)
- confidence: high

### [8] Firebase не делает merge данных при коллизии сам: linkWithCredential падает, если кред уже привязан к другому пользователю, и merge — обязанность приложения (официальный sample: signInWithCredential → repo.merge → deleteUser(prevUser)).
- quote: "Account linking will fail if the credentials are already linked to another user account. In this situation, you must handle merging the accounts and associated data as appropriate for your app"
- url: https://firebase.google.com/docs/auth/web/account-linking
- source_type: primary
- published: unknown (fetched 2026-10-29)
- confidence: high

### [9] Firebase различает "email IdP" (авторитетен для своего домена) и "social IdP" (разово подтвердивший e-mail): для Google-аккаунтов, хостинг которых у Google, ошибка account-exists-with-different-credential не возникает даже при существующем password/social-аккаунте.
- quote: "Google serves as both an email and social identity provider. Email IDPs are authoritative for all email addresses related to their hosted email domain while social IDPs assert email identities based having done a one time confirmation of the email address. A user logging in with Google will never cause this error when their account is hosted at Google even if they signed up for their account with a password or a social IDP."
- url: https://firebase.google.com/docs/auth/web/google-signin
- source_type: primary
- published: unknown (fetched 2026-10-29)
- confidence: medium (формулировка официальная, но семантика "hosted at Google" на странице не раскрыта точнее)

### [10] Auth0 не документирует авто-merge при совпадении e-mail; официальный паттерн "Suggested Account Linking" — найти аккаунты через GET /api/v2/users-by-email (scope read:users), показать пользователю список совпадений, предложить линк, подтвердить владение вторым аккаунтом через его credentials, затем POST /users/{id}/identities.
- quote: "Your application will then prompt the user to link their accounts by authenticating with the target account's credentials, and later link the accounts... If Auth0 returns one or more records with matching email addresses, the user will see the list along with the following message prompting them to link the accounts."
- url: https://auth0.com/docs/manage-users/user-accounts/user-account-linking/suggested-account-linking-server-side-implementation
- source_type: primary
- published: unknown (fetched 2026-10-29)
- confidence: high

### [11] Auth0 требует аутентификации обеих сторон перед линком ("Every manual account link should prompt the user to enter credentials") и разрешает линк только к верифицированному аккаунту — авто-линк без проверок трактуется как вектор захвата аккаунта.
- quote: "Every manual account link should prompt the user to enter credentials . Your tenant should request authentication for both accounts before linking occurs to avoid allowing malicious actors to access legitimate user accounts." (также в sample-коде: "Account linking is only allowed to a verified account.")
- url: https://auth0.com/docs/manage-users/user-accounts/user-account-linking/link-user-accounts (quote "Every manual...") и https://auth0.com/docs/manage-users/user-accounts/user-account-linking/user-initiated-account-linking-client-side-implementation (quote "only allowed to a verified account")
- source_type: primary
- published: unknown (fetched 2026-10-29)
- confidence: high

### [12] WorkOS AuthKit: identity linking дедуплицирует креды по e-mail как уникальному идентификатору, но источник истины — доступ к почтовому ящику; новый кред автоматически прикрепляется к существующему юзеру только после верификации доступа к инбоксу, иначе authentication flow не завершается (block).
- quote: "It does this by using the email address as the unique identifier and access to the email inbox as the source of truth... This is only performed if WorkOS can verify that the user has access to the email inbox referenced by that credential... WorkOS does not complete the authentication flow when a new identity cannot be safely linked to an existing user to ensure account takeover risks are minimized."
- url: https://workos.com/docs/authkit/identity-linking
- source_type: primary
- published: unknown (fetched 2026-10-29)
- confidence: high

## Dead ends
- WebSearch-инструмент в сессии недоступен (plugin disabled) — вместо поиска использованы известные URL официальной документации + curl-фетчи; полнота покрытия темы через поиск не проверена.
- Auth0 «User Account Linking» overview (user-account-linking) отдаёт только nav-JSON без тела статьи (client-side render) — политика link/merge восстановлена по трём сабпейджам (link-user-accounts, suggested-account-linking-server-side-implementation, user-initiated-account-linking-client-side-implementation).
- Clerk /docs/users/external-accounts — JS-shell без тела (44 символа текста); взят профильный гайд account-linking, который оказался полнее.
- Passkeys/WebAuthn: нашлись только nav-упоминания (Auth0 «Configure WebAuthn with Device Biometrics for Passwordless Authentication», WorkOS «Passkeys») — ни один фетчнутый источник не документирует passkey-инициированный link-identity flow при коллизии e-mail.
- Единого задокументированного "magic link/OTP как proof-of-inbox при линке" терминологического слоя у вендоров нет: у всех это сводится к абстрактной "email verification" (Supabase/Clerk/WorkOS/Auth0) — отдельные страницы про роль именно OTP vs magic link в linking flow не найдены среди фетчнутых.

## Suggested follow-ups
- Firebase: семантика console-переключателя "One account per email address" и статус fetchSignInMethodsForEmail (email enumeration protection) — напрямую влияет на выбор OTP-first vs password-first при совпадении e-mail.
- Auth0 sample-приложение auth0-samples/auth0-link-accounts-sample (RegularWebApp): UX-копирайт экрана "found N accounts with your email" — готовый паттерн подсказки при совпадении.
- NIST SP 800-63B / OWASP: требования к верификации контролируемого идентификатора (email OTP vs одноразовый magic-link токен) как нормативное обоснование OTP-привязки вместо пароля.
