# F4: UX-практика решения «user already exists» при входе из приложения маркетплейса: pending link, merge accounts, confirm-by-email — что выбирают чаще и почему (форумы, community, guides).

## Findings

### [1] Крупные IAM-платформы по умолчанию разводят аккаунты и не линкуют автоматически: Auth0 treats all identities as separate by default и рекомендует два явных флоу — user-initiated linking (кнопка «Link accounts» в профиле после логина) и suggested account linking (найти аккаунты с тем же e-mail и предложить пользователю залогиниться в целевой аккаунт и подтвердить линк).
- quote: "Auth0 treats all identities as separate by default... You can implement functionality to enable a user to explicitly link accounts... Suggested account linking: identify accounts with the same email address and prompt the user in your app to link them."
- url: https://auth0.com/docs/manage-users/user-accounts/user-account-linking
- source_type: primary
- published: unknown (current docs, fetched 2026-10-29)
- confidence: high

### [2] Auth0 прямо предупреждает, что небезопасный линк ведёт к захвату аккаунта, и требует аутентифицировать ОБА аккаунта до линка; каждый ручной линк должен спрашивать credentials существующего аккаунта.
- quote: "Insecurely linking accounts can allow malicious actors to access legitimate user accounts... your tenant should request authentication for both accounts before linking occurs. In addition, every manual account link should prompt the user to enter credentials."
- url: https://auth0.com/docs/manage-users/user-accounts/user-account-linking
- source_type: primary
- published: unknown (current docs, fetched 2026-10-29)
- confidence: high

### [3] Merge accounts в Auth0 не бывает автоматическим: линковка встраивает secondary identity в профиль primary, метаданные secondary (user_metadata/app_metadata) отбрасываются, автоматического слияния профилей нет — только вручную через Management API.
- quote: "There is no automatic merging of user profiles with associated identities... The user_metadata and app_metadata of the secondary account are discarded... If you want to merge it, you have to do it manually using the Manage API"
- url: https://auth0.com/docs/manage-users/user-accounts/user-account-linking
- source_type: primary
- published: unknown (current docs, fetched 2026-10-29)
- confidence: high

### [4] Firebase автоматически линкует одинаковый e-mail только если ОБА провайдера — доверенные верификаторы e-mail (Google для @gmail.com, Yahoo для @yahoo.com, Microsoft для @outlook.com/@hotmail.com, Apple всегда); в остальных случаях кидает ошибку «requiring account linking», и это сделано осознанно из-за сценария захвата аккаунта.
- quote: "a user signs in using Google with a @gmail.com account and a malicious actor creates an account using the same @gmail.com address, but signing in via Facebook. If these two accounts were automatically linked, the malicious actor would gain access to the user's account."
- url: https://firebase.google.com/docs/auth/users#verified_email_addresses
- source_type: primary
- published: 2026-10-20 (last updated)
- confidence: high

### [5] Матрица Firebase: untrusted→untrusted (Facebook→GitHub) и trusted→untrusted (Google→Facebook) дают «an error requiring account linking», т.е. явный ручной/подтверждаемый линк; авто-линк есть только trusted+trusted (Apple→Google «linked without errors») и untrusted→trusted (trusted перезаписывает).
- quote: "This throws an error requiring account linking... Both providers will be linked without errors."
- url: https://firebase.google.com/docs/auth/users#verified_email_addresses
- source_type: primary
- published: 2026-10-20 (last updated)
- confidence: high

### [6] Firebase-флоу линка всегда «сначала аутентификация существующего аккаунта, потом линк» (linkWithPopup/linkWithCredential на уже залогиненном currentUser), а если credential уже привязан к другому юзеру — «you must handle merging the accounts... as appropriate for your app» (их пример вручную мержит данные и удаляет prevUser): merge вынесен в приложение, платформа его не делает.
- quote: "Sign in the user using any authentication provider or method... Account linking will fail if the credentials are already linked to another user account. In this situation, you must handle merging the accounts and associated data as appropriate for your app"
- url: https://firebase.google.com/docs/auth/web/account-linking
- source_type: primary
- published: 2026-10-21 (last updated)
- confidence: high

### [7] Clerk при совпадении e-mail OAuth и существующего аккаунта линкует автоматически, только если e-mail верифицирован с обеих сторон (даже минуя пароль); если e-mail верифицирован в Clerk но не в OAuth — запускает верификацию e-mail (confirm-by-email) и лишь потом линкает: email-подтверждение — стандартный посерединный механизм между авто-линком и ручным.
- quote: "Clerk links the OAuth account to the existing account and signs the user in. This even applies to password-protected accounts... Clerk will initiate a verification process. Once the email address is verified, the OAuth account is linked to the existing one"
- url: https://clerk.com/docs/guides/configure/auth-strategies/social-connections/account-linking
- source_type: primary
- published: unknown (current docs, fetched 2026-10-29)
- confidence: high

### [8] Clerk при неверифицированном e-mail существующего (password) аккаунта перед линком требует сменить пароль и пройти верификацию, потому что «cannot confirm the original ownership of the account» — т.е. подтверждение владения e-mail/аккаунтом обязательно, когда доверия к e-mail нет.
- quote: "Clerk will prompt the user to change their password before linking the accounts... These measures are in place because Clerk cannot confirm the original ownership of the account, which could otherwise lead to unauthorized access."
- url: https://clerk.com/docs/guides/configure/auth-strategies/social-connections/account-linking
- source_type: primary
- published: unknown (current docs, fetched 2026-10-29)
- confidence: high

### [9] Clerk strict user-enumeration protection: при signup на уже существующий e-mail не отправляется код верификации и не раскрывается существование аккаунта — вместо этого уведомление уходит владельцу аккаунта; existence раскрывается только после верификации личности — практика «не показывать "account exists" анонимному посетителю».
- quote: "If you sign up with an email or phone number that already exists, Clerk won't send a verification code. Instead, it sends a notification (email or SMS) letting the account owner know someone tried to..."
- url: https://clerk.com/docs/guides/protect/user-enumeration-protection
- source_type: primary
- published: unknown (current docs, fetched 2026-10-29)
- confidence: high

### [10] Auth.js/NextAuth v5 (февраль 2024) по умолчанию блокирует OAuth-вход на существующий e-mail ошибкой OAuthAccountNotLinked; авто-линк — только через opt-in флаг allowDangerousEmailAccountLinking «if you trust the OAuth provider to have verified the user's email address», и community (issue #9992) жалуется именно на UX-цену безопасного дефолта («I shouldn't have to enable a dangerous flag just so a user can log in twice»).
- quote: "If you trust the OAuth provider to have verified the user's email address, you can enable automatic account linking by setting allowDangerousEmailAccountLinking: true... I shouldn't have to enable a dangerous flag just so a user can log in twice"
- url: https://github.com/nextauthjs/next-auth/issues/9992
- source_type: community
- published: 2024-02-11 (issue opened; closed 2024-02-14 in #10008, fix in 5.0.0-beta.11)
- confidence: high

### [11] django-allauth (дефолт, 2025): OAuth-вход на существующий e-mail шлёт письмо «Account Already Exists» со ссылкой на password reset — issue wafer-space #22 называет это misleading UX и предлагает вместо этого экран с кнопками «Login and link this provider» и «Use password recovery» + списком уже привязанных методов входа; бэкенд-автолинковка при этом работает и без того (SOCIALACCOUNT_AUTO_SIGNUP / SOCIALACCOUNT_EMAIL_AUTHENTICATION), проблема чисто UX (P2).
- quote: "Instead it would be good to offer them to login using the currently valid methods and connect this authentication method with the current account... Intermediate 'confirmation email sent' message is misleading... User should be prompted to login and link accounts in one flow"
- url: https://github.com/wafer-space/platform.wafer.space/issues/22
- source_type: community
- published: 2025-09-28 (issue opened; обновлён 2025-10-04)
- confidence: high

### [12] Better Auth (актуальный TS-фреймворк, преемник Auth.js): дефолт — implicit linking при совпадении e-mail, если провайдер верифицировал e-mail или есть в trustedProviders; для «confirm linking from a settings page rather than implicitly on sign-in» есть disableImplicitLinking: true (тогда кидается account_not_linked, а резолв — «Ask users to sign in using the originally linked provider or method»); forced linking через trustedProviders помечен «may increase the risk of account takeover».
- quote: "By default, when a user signs in with an OAuth provider whose email matches an existing user (and either the provider verified the email or it is in trustedProviders), Better Auth automatically links the OAuth account... Use this when you want users to confirm linking from a settings page rather than implicitly on sign-in."
- url: https://better-auth.com/docs/concepts/users-accounts
- source_type: primary
- published: unknown (v1.7 latest per better-auth.com/docs/llms.txt, fetched 2026-10-29)
- confidence: high
