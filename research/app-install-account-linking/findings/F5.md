# F5: InSales-специфика: что официальные доки InSales говорят про user-identity в app-колбэках (user_email, email_confirmed, token3) и рекомендации по онбордингу/входу в приложение.

## Findings

### [1] Колбэк установки приложения (GET на «URL установки») не содержит никакой user-identity — только `shop`, `insales_id` и одноразовый `token` для расчёта пароля `password = MD5(token + secret)`.
- quote: "GET https://myapp.example/install?shop=demo.myinsales.ru&token=TOKEN&insales_id=123 … `token` | Одноразовая строка для расчёта пароля. … Вычислите пароль по формуле `password = MD5(token + secret)`"
- url: https://raw.githubusercontent.com/insales/insales-docs-source/master/docs/InSales%20API/01%20readme.md
- source_type: primary
- published: 2026-10-22 (последний коммит файла в официальном репо insales/insales-docs-source)
- confidence: high

### [2] Идентичность пользователя (`user_id`, `user_email`) появляется только при входе через «URL входа» — как неподписанные GET-параметры, не как авторизационное доказательство.
- quote: "GET https://myapp.example/login?shop=demo.myinsales.ru&insales_id=123&user_id=USER_ID&user_email=USER_EMAIL … В этом запросе `shop` и `insales_id` определяют магазин, а `user_id` и `user_email` — пользователя."
- url: https://raw.githubusercontent.com/insales/insales-docs-source/master/docs/InSales%20API/01%20readme.md
- source_type: primary
- published: 2026-10-22
- confidence: high

### [3] Официальная рекомендация: получения `user_email`/`user_id` из URL входа НЕДОСТАТОЧНО для входа — если сессии приложения ещё нет, пользователя обязательно подтверждать через автологин InSales.
- quote: "Самого получения этих параметров недостаточно для входа: если сессии приложения ещё нет, подтвердите пользователя через автологин InSales."
- url: https://docs.liquidhub.ru/InSales%20API/01%20readme/
- source_type: primary
- published: 2026-10-22
- confidence: high

### [4] Единственный официальный механизм верификации identity — автологин: приложение генерирует одноразовый LOGIN_TOKEN и редиректит браузер на `https://<shop>/admin/applications/<app_id>/login?token=LOGIN_TOKEN&login=<autologin_url>`; InSales возвращает подписанную связку параметров.
- quote: "Создайте одноразовый токен для входа и сохраните его до проверки ответа. Он не связан с токеном установки. Перенаправьте браузер пользователя на адрес автологина магазина: GET https://demo.myinsales.ru/admin/applications/my_app/login?token=LOGIN_TOKEN&login=https%3A%2F%2Fmyapp.example%2Fautologin"
- url: https://raw.githubusercontent.com/insales/insales-docs-source/master/docs/InSales%20API/01%20readme.md
- source_type: primary
- published: 2026-10-22
- confidence: high

### [5] `token3 = MD5(LOGIN_TOKEN + user_email + user_name + user_id + email_confirmed + password)` — подпись связывает identity, флаг подтверждения почты и пароль приложения в магазине; доки требуют вычислить token3, создать сессию ТОЛЬКО после успешной проверки, отклонить вход при несовпадении, токен входа одноразовый.
- quote: "`token3` | `MD5(LOGIN_TOKEN + user_email + user_name + user_id + email_confirmed + password)` … Создавайте сессию пользователя только после успешной проверки. Если значения не совпали, отклоните вход. Токен входа используйте один раз."
- url: https://docs.liquidhub.ru/InSales%20API/01%20readme/
- source_type: primary
- published: 2026-10-22
- confidence: high

### [6] `email_confirmed` — строка `"true"` или `"false"`: подтверждён ли адрес почты пользователем; т.е. InSales прямо сообщает, что e-mail из колбэка может быть НЕ подтверждённым, и этот флаг вшит в token3 (не подделать без пароля магазина).
- quote: "`email_confirmed` | Строка `true` или `false`: подтверждён ли адрес почты."
- url: https://docs.liquidhub.ru/InSales%20API/01%20readme/
- source_type: primary
- published: 2026-10-22
- confidence: high

### [7] В колбэке автологина есть и более старая подпись `token2 = MD5(LOGIN_TOKEN + user_email + user_name + user_id + password)` — без `email_confirmed`; актуальная спецификация — token3, а сам LOGIN_TOKEN использовать один раз.
- quote: "`token2` | `MD5(LOGIN_TOKEN + user_email + user_name + user_id + password)` … `token3` | `MD5(LOGIN_TOKEN + user_email + user_name + user_id + email_confirmed + password)`"
- url: https://raw.githubusercontent.com/insales/insales-docs-source/master/docs/InSales%20API/01%20readme.md
- source_type: primary
- published: 2026-10-22
- confidence: high

### [8] Официальная модель сессии: первый вход — через автологин; если сессия приложения уже есть, повторный вход из админки открывает UI без нового автологина (т.е. платформа закладывает «один раз подтвердили — дальше сессия»).
- quote: "Если сессия приложения уже есть, при повторном переходе можно открыть интерфейс приложения без нового автологина."
- url: https://docs.liquidhub.ru/InSales%20API/01%20readme/
- source_type: primary
- published: 2026-10-22
- confidence: high

### [9] Назначение token3 по старым официальным материалам InSales — доказать, что пользователь действительно залогинен в бэк-офис InSales, а не подделал URL; это proof-of-InSales-session, а не proof-of-email-ownership.
- quote: "По этому token можно убедиться, что пользователь действительно логинен в магазин на inSales, а не подделал этот урл."
- url: /home/chubuk/projects/mcp-is/docs/api/api_and_apps.md (локальное зеркало «материалов с сайта insales.ru для разработчиков внешних приложений», §«Процедура автологина пользователя»)
- source_type: primary
- published: unknown (зеркало в репо mcp-is, коммит 0304166)
- confidence: high

### [10] Требование безопасности автологина: домен обработчика автологина должен совпадать с доменом «URL входа» из настроек приложения (InSales проверяет домен второго уровня).
- quote: "Домен обработчика должен совпадать с доменом URL входа из настроек приложения: InSales проверяет домен второго уровня."
- url: https://raw.githubusercontent.com/insales/insales-docs-source/master/docs/InSales%20API/01%20readme.md
- source_type: primary
- published: 2026-10-22
- confidence: high

### [11] Поколения доков согласованы: и старые материалы insales.ru, и текущие доки описывают установку одинаково (`token`, `shop`, `insales_id`, `password = MD5(token + secret_key)`), user-identity на установку не передаётся ни в одной версии.
- quote: "После этого отправляется GET запрос на URL для установки приложений с параметрами `token`, `shop` и `insales_id` … `password = MD5(token + secret_key)`"
- url: /home/chubuk/projects/mcp-is/docs/api/api_and_apps.md (§«Процедура установки»)
- source_type: primary
- published: unknown

### [12] Комьюнити-SDK (insales_app_go/ruby/php/node/python, VladimirIvanin) реализуют ту же формулу token3 и фиксируют, что `email_confirmed` — литеральная строка "true"/"false"; альтернативных схем верификации identity в экосистеме не видно.
- quote: "Token3 computes the third-generation InSales autologin token. … MD5(nonce + user_email + user_name + user_id + email_confirmed + password) … email_confirmed must be the literal string \"true\" or \"false\"."

### [13] Официальные доки InSales НЕ содержат рекомендаций по выбору механизма первой привязки к существующему аккаунту приложения (пароль/OTP/авто-линк): модель платформы — «InSales-сессия = провайдер идентичности», аккаунт приложения целиком на совести интегратора; вопросы по приложениям адресованы на partners@insales.ru.
