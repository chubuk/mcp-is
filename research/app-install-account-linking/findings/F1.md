# F1: Как крупные маркетплейсы приложений (Shopify, Bitrix24, Wix, Tilda) передают идентичность пользователя при установке приложения и что происходит при совпадении e-mail с существующим аккаунтом сервиса.

## Findings

### [1] Shopify передаёт идентичность пользователя приложению через короткоживущий ID token (JWT): claims `sub` (ID пользователя Shopify) + `dest` (магазин), e-mail в токене отсутствует — ключом идентичности служит платформенный user ID, а не e-mail.
- quote: "An ID token ... is a short-lived JWT that App Bridge issues to your embedded app to prove a request comes from an authenticated Shopify user ... sub: The user the token was issued for."
- url: https://shopify.dev/docs/apps/build/authentication-authorization/id-tokens
- source_type: primary
- published: unknown (fetched 2026-10-29)
- confidence: high

### [2] Пример декодированного payload Shopify ID token подтверждает: идентификаторы — `iss`/`dest` (домен магазина), `sub` (числовой ID пользователя, например "42"), `sid` (сессия), никакого claim с e-mail.
- quote: '"iss": "https://exampleshop.myshopify.com/admin", "dest": "https://exampleshop.myshopify.com", "aud": "client-id-123", "sub": "42", ... "sid": "aaea182f..."}'
- url: https://shopify.dev/docs/apps/build/authentication-authorization/id-tokens
- source_type: primary
- published: unknown (fetched 2026-10-29)
- confidence: high

### [3] В Shopify онлайн-токены привязаны к конкретному сотруднику (staff member), который дал авторизацию, т.е. атрибуция действий идёт по платформенному пользователю; оффлайн-токены переживают сессии — модель «магазин + пользователь магазина», а не «e-mail сервиса».
- quote: "An online access token ... is narrowed to the staff member who authorized it, so a request can be refused even when you hold the scope."
- url: https://shopify.dev/docs/apps/build/authentication-authorization
- source_type: primary
- published: unknown (fetched 2026-10-29)
- confidence: high

### [4] Bitrix24 проектирует полный OAuth 2.0 для внешних сервисов с предположением, что у сервиса уже есть свой аккаунт пользователя («пользователь уже авторизован в вашем сервисе») — маркетплейс не занимается привязкой аккаунтов вендора, это зона ответственности вендора.
- quote: "Полный протокол нужен приложению, которое работает за пределами интерфейса Битрикс24 и хранит токены на своей стороне. ... пользователь уже авторизован в вашем сервисе"
- url: https://apidocs.bitrix24.ru/settings/oauth/index.html
- source_type: primary
- published: unknown (fetched 2026-10-29)
- confidence: high

### [5] При OAuth-авторизации в Bitrix24 на redirect_uri приложения передаются `code`, `state`, `domain`, `member_id` (уникальный ID портала, не меняется при смене адреса), `scope`, `server_domain` — e-mail пользователя не передаётся вовсе; идентичность = (member_id, домен портала).
- quote: "member_id — Уникальный идентификатор Битрикс24, который не меняется при смене адреса"
- url: https://apidocs.bitrix24.ru/settings/oauth/index.html
- source_type: primary
- published: unknown (fetched 2026-10-29)
- confidence: high

### [6] В Bitrix24 REST-вызовы приложения выполняются от имени конкретного пользователя, прошедшего авторизацию, и ограничены его правами на портале — идентичность пользователя выражена в правах/контексте токена, а не в e-mail.
- quote: "Вызовы методов выполняются от имени пользователя, прошедшего авторизацию, и ограничены его правами в Битрикс24."
- url: https://apidocs.bitrix24.ru/settings/oauth/index.html
- source_type: primary
- published: unknown (fetched 2026-10-29)
- confidence: high

### [7] Bitrix24 при установке тиражного (marketplace) приложения может создать «системного пользователя» (RESOURCE_TYPE: APP) и отдать приложению его токены событием ONAPPUSERREADY — авторизация приложения декаплится от сотрудника-установщика и переживает его увольнение.
- quote: "флажок включен — Битрикс24 создает системного пользователя и отправляет приложению событие ONAPPUSERREADY с его авторизацией ... Его авторизация не зависит от сотрудника, который установил приложение, и продолжает работать после его увольнения."
- url: https://apidocs.bitrix24.ru/settings/system-user.html
- source_type: primary
- published: unknown (fetched 2026-10-29)
- confidence: high

### [8] В Bitrix24 установка приложения без UI передаёт токены (access_token + refresh_token) POST-запросом на callback-обработчик сразу после установки — «пользовательский» контекст первичной привязки отсутствует, приложение привязывается к порталу (member_id) через токены.
- quote: "Сразу после добавления локального приложения Битрикс24 автоматически обратится к этому URL и передаст туда POST-запрос с данными авторизации OAuth 2.0, включая access_token и refresh_token."
- url: https://apidocs.bitrix24.ru/settings/app-installation/local-apps/installation-callback.html
- source_type: primary
- published: unknown (fetched 2026-10-29)
- confidence: high

### [9] Wix: установка приложения из App Market — это OAuth-флоу выдачи прав, который целиком ведёт сам Wix («Wix handles the full flow and manages authentication»); никакой передачи/сверки e-mail вендору при установке не описано.
- quote: "When a Wix user installs your app, Wix runs an app install flow, an OAuth authentication process that grants your app the permissions you've configured in the app dashboard. ... Wix handles the full flow and manages authentication."
- url: https://dev.wix.com/docs/build-apps/launch-your-app/app-distribution/install-your-app/about-app-installation
- source_type: primary
- published: 2026-04-19 (last updated; fetched 2026-10-29)
- confidence: high

### [10] Модель идентичности Wix — стабильные платформенные ID и роли (Visitor / Member / Wix user / Wix app / API key admin): у Wix user есть user ID и account ID, member ID персистентен, «contact» и «member» — разные сущности с разными ID; e-mail не выступает ключом идентичности.
- quote: "A Wix user is a site owner or collaborator. Each Wix user has a user ID and can belong to multiple Wix accounts ... A member is an authenticated identity. Each member links to a contact, but their IDs are different."
- url: https://dev.wix.com/docs/overview/auth-permissions/identities
- source_type: primary
- published: 2026-08-02 (last updated; fetched 2026-10-29)
- confidence: high

### [11] Wix различает три уровня аутентификации приложения: как app instance (установка на сайт), «от имени Wix user» (права приложения ∩ права пользователя) и «от имени visitor/member»; опция «on behalf of a Wix user» доступна только для dashboard-страниц — т.е. идентичность установщика = Wix user ID с ролями, а не e-mail.
- quote: "Your app can authenticate on behalf of a Wix user to get an access token that includes the permissions granted to both the app and the user. ... Important: This authentication approach is only supported for dashboard pages."
- url: https://dev.wix.com/docs/build-apps/develop-your-app/auth/about-authentication
- source_type: primary
- published: 2026-08-31 (last updated; fetched 2026-10-29)
- confidence: high

### [12] У Tilda нет маркетплейса приложений с install-time передачей идентичности: интеграция выполняется через пару ключей аккаунта `publickey`/`secretkey` (Настройки сайта → Экспорт → API, тариф Business), запросы GET на api.tildacdn.info, лимит 150 запросов/час; webhook при публикации несёт `pageid, projectid, published, publickey` — аккаунтный ключ, а не пользователь.
- quote: "взаимодействие с API доступно только для тарифа Business. Для начала вам нужно получить publickey и secretkey ... В каждом запросе необходимо передавать переменные: publickey и secretkey"
- url: https://help-ru.tilda.cc/api
- source_type: primary
- published: unknown (fetched 2026-10-29)
- confidence: high

### [13] Синтез: ни Shopify, ни Bitrix24, ни Wix, ни Tilda не выполняют привязки к существующему аккаунту сервиса вендора по совпадению e-mail — маркетплейсы передают стабильные платформенные идентификаторы (sub+dest / member_id+domain / user-id и app instance / account API keys), а поведение при совпадении e-mail остаётся полностью на стороне вендора приложения (у Bitrix24 это прямо зафиксировано предположением «пользователь уже авторизован в вашем сервисе»).
- quote: "Полный протокол нужен приложению ... пользователь уже авторизован в вашем сервисе"
- url: https://apidocs.bitrix24.ru/settings/oauth/index.html
- source_type: primary
- published: unknown (fetched 2026-10-29)
- confidence: medium

## Dead ends
- WebSearch-инструмент недоступен (plugin disabled); поиск выполнен обходом через DuckDuckGo/Mojeek (заблокировали бот-запросы) и Bing HTML.
- developers.tilda.cc не отдаёт контент (пустой ответ) — документация Tilda для разработчиков приложений не найдена; подтверждено, что Tilda API — ключи аккаунта, а не OAuth-маркетплейс.
- Ни в одном из официальных документации Shopify/Bitrix24/Wix/Tilda не описано поведение «e-mail совпал с существующим аккаунтом сервиса вендора» — этого сценария просто нет в протоколах установки (вывод зафиксирован в [13]).
- Не найдено официального описания передачи e-mail пользователя при установке: Shopify ID token не содержит e-mail claim, Bitrix24 OAuth-redirect не содержит e-mail.

## Suggested follow-ups
- Bitrix24 REST `profile` (oauth/userinfo): возвращает ли метод e-mail авторизованного пользователя — как вендору получить верифицированный e-mail для своей привязки?
- Shopify: как приложению получить e-mail текущего staff-пользователя (Shop GraphQL `currentUser` / Users REST) и верифицирован ли он Shopify — это определяет, можно ли делать auto-link по e-mail.
- Google Identity / OIDC account linking по `email_verified`: сравнительный базис для выбора OTP vs auto-link в mcp-is.
