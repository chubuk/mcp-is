# F4: Security, auth, multi-tenancy, transport

## Findings

### [1] The MCP authorization spec (rev. 2026-07-28) defines a mandatory OAuth 2.1 subset for HTTP transports: OAuth 2.1 draft-ietf-oauth-v2-1-13, RFC 6750 bearer tokens, RFC 8414/OIDC discovery, RFC 8707 Resource Indicators, RFC 9728 Protected Resource Metadata, and RFC 9207 issuer identification; auth itself is OPTIONAL but if present, HTTP implementations SHOULD conform.
- quote: "Authorization servers MUST implement OAuth 2.1 with appropriate security measures for both confidential and public clients."
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/authorization/index.mdx
- source_type: primary
- published: 2026-07-28 (spec revision)
- confidence: high

### [2] MCP servers must reject any access token not issued for them specifically (audience validation per RFC 8707/9068); "token passthrough" (forwarding the client's token to upstream APIs) is explicitly forbidden — an upstream call needs a separate token minted for the upstream AS.
- quote: "MCP servers MUST only accept tokens that are valid for use with their own resources. MCP servers MUST NOT accept or transit any other tokens."
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/authorization/security-considerations.mdx
- source_type: primary
- published: 2026-07-28 (spec revision)
- confidence: high

### [3] As of 2026-07-28, OAuth 2.0 Dynamic Client Registration (RFC 7591) is deprecated in MCP and retained only for backward compatibility; Client ID Metadata Documents (URL-as-client_id, draft-ietf-oauth-client-id-metadata-document) are the SHOULD mechanism, with SSRF and localhost-redirect-impersonation caveats for AS implementers.
- quote: "Dynamic Client Registration is deprecated and retained for backwards compatibility with authorization servers that do not support Client ID Metadata Documents."
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/authorization/index.mdx
- source_type: primary
- published: 2026-07-28 (spec revision)
- confidence: high

### [4] PKCE is mandatory for MCP clients: S256 challenge method when technically capable, and clients MUST refuse to proceed if the AS metadata lacks `code_challenge_methods_supported` (also required of OIDC providers for MCP compatibility).
- quote: "If `code_challenge_methods_supported` is absent, the authorization server does not support PKCE and MCP clients MUST refuse to proceed."
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/authorization/security-considerations.mdx
- source_type: primary
- published: 2026-07-28 (spec revision)
- confidence: high

### [5] The 2026 spec formalizes least-privilege scope economy: `scopes_supported` should be a minimal baseline, servers advertise per-operation scopes via `WWW-Authenticate` challenges (403 `error="insufficient_scope"`), and clients run a "step-up authorization" flow taking the union of old + challenged scopes — relevant to a ~245-tool server where omnibus scopes are called out as a common mistake.
- quote: "Minimal initial scope set (e.g., `mcp:tools-basic`) containing only low-risk discovery/read operations … Incremental elevation via targeted `WWW-Authenticate` `scope=\"...\"` challenges when privileged operations are first attempted"
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/docs/2026-07-28/tutorials/security/security_best_practices.mdx
- source_type: primary
- published: 2026-07-28 (docs revision)
- confidence: high

### [6] Revision 2026-07-28 of Streamable HTTP removed protocol-level sessions entirely (`Mcp-Session-Id` gone, no GET standalone SSE stream, no `Last-Event-ID` resumability): MCP is now stateless per request; long-lived server→client notifications moved to `subscriptions/listen`, and server→client interactions (sampling/elicitation/roots) moved to in-band MRTR `InputRequiredResult` (SEP-2322).
- quote: "Revision 2026-07-28 changed the behavior of Streamable HTTP … Removal of the GET stream endpoint. Removal of protocol-level sessions."
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/transports/streamable-http.mdx
- source_type: primary
- published: 2026-07-28 (spec revision)
- confidence: high

### [7] The 2025-11-25 Streamable HTTP session model (still what most servers including mark3labs/mcp-go v0.56 implement) is: optional `Mcp-Session-Id` minted at initialize — "SHOULD be globally unique and cryptographically secure" — echoed on every request (else 400), server may terminate (then 404), client SHOULD close with HTTP DELETE; this whole model is retired in 2026-07-28.
- quote: "The session ID SHOULD be globally unique and cryptographically secure … Clients that no longer need a particular session … SHOULD send an HTTP DELETE to the MCP endpoint with the `MCP-Session-Id` header, to explicitly terminate the session."
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2025-11-25/basic/transports.mdx
- source_type: primary
- published: 2025-11-25 (spec revision)
- confidence: high

### [8] Since the protocol is now stateless, any multi-request state (carts, workflows, "shop context") is an explicit opaque handle passed back as a tool argument — and the spec names "state handle hijacking" as an attack: handles MUST NOT be treated as authentication and SHOULD be bound server-side to the token-derived user id (e.g. keying state as `<user_id>:<handle>`).
- quote: "MCP servers MUST NOT treat possession of a state handle as authentication."
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/docs/2026-07-28/tutorials/security/security_best_practices.mdx
- source_type: primary
- published: 2026-07-28 (docs revision)
- confidence: high

### [9] Streamable HTTP servers MUST validate the `Origin` header (403 on invalid) against DNS rebinding, SHOULD bind localhost-only when local and SHOULD authenticate all connections; the older HTTP+SSE transport (2024-11-05) is formally Deprecated since protocol version 2025-03-26 and eligible for removal.
- quote: "Servers MUST validate the `Origin` header on all incoming connections to prevent DNS rebinding attacks."
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/transports/streamable-http.mdx
- source_type: primary
- published: 2026-07-28 (spec revision)
- confidence: high

### [10] The "confused deputy" attack on MCP proxies (static client ID + dynamic client registration + third-party consent cookie skips consent) is documented with a normative mitigation: proxies MUST implement per-client consent (registry of approved client_ids, consent UI showing client name/scopes/redirect_uri, CSRF-protected, exact redirect_uri matching) before forwarding to the third-party AS.
- quote: "MCP proxy servers using static client IDs MUST obtain user consent for each dynamically registered client before forwarding to third-party authorization servers"
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/authorization/security-considerations.mdx
- source_type: primary
- published: 2026-07-28 (spec revision)
- confidence: high

### [11] To make gateway-level multi-tenant routing/rate-limiting safe without parsing bodies, 2026-07-28 Streamable HTTP requires mirrored request-metadata headers (`MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`, optional `Mcp-Param-*` via `x-mcp-header`); servers MUST reject header/body divergence with JSON-RPC error `-32020 HeaderMismatch`, and intermediaries rate-limiting by tenant SHOULD reject requests whose protocol version doesn't enforce header-body validation.
- quote: "Intermediaries that enforce policy based on mirrored headers (e.g., routing or rate-limiting by tenant) SHOULD verify that the `MCP-Protocol-Version` header indicates a version that requires header–body validation."
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/transports/streamable-http.mdx
- source_type: primary
- published: 2026-07-28 (spec revision)
- confidence: high

### [12] Peer-reviewed 2026 research finds a systematic least-privilege gap called "filesystem capability laundering": client-side approval of an MCP tool call typically grants the server process broad host filesystem rights beyond the tool's declared contract, and attacker-steered arguments reach files outside the declared scope (MCP-FSD measures this across L1 category screening, L2 per-tool contract analysis, L3 path-validation bypasses).
- quote: "In typical local deployments, client-side approval of a tool call grants the underlying server process broad host filesystem permissions rather than restricting it to the declared operation."
- url: https://arxiv.org/abs/2610.22301
- source_type: primary
- published: 2026-10-15
- confidence: high

### [13] A second 2026 study ("Approve What, Exactly?") shows MCP elicitation/step-up approvals are often not binding: across 8 agent runtimes with measurable binding, 4 allowed post-approval argument changes, and an audit of 10 runtimes found no third-party-verifiable approval record and no flood limits — i.e. production MCP servers cannot rely on client-side approval prompts as a security control.
- quote: "An audit of ten agent runtimes finds no third-party verifiable approval record, no flood limits where measurable, and post-approval argument changes in four of eight runtimes with measurable binding."
- url: https://arxiv.org/abs/2610.21063
- source_type: primary
- published: 2026-10-15
- confidence: high

### [14] Ecosystem/SDK expectation (mark3labs/mcp-go, the library mcp-is builds on): remote servers are expected to expose `/.well-known/oauth-protected-resource` (RFC 9728) metadata, and multi-tenant tool exposure is done via `WithToolFilter` (per-session tool lists) and `SessionWithTools` — the library provides session-scoped filtering but no built-in auth enforcement or rate limiting.
- quote: "You can also apply filters to control which tools are available to certain sessions"
- url: https://raw.githubusercontent.com/mark3labs/mcp-go/main/README.md
- source_type: primary
- published: unknown (repo main branch, fetched 2026-10-20)
- confidence: high

- No dedicated MCP rate-limiting or audit-logging standard was found; the spec only names these as controls that token passthrough would bypass, and as policy that intermediaries may enforce via mirrored headers.
