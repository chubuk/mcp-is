# F1: MCP protocol & official spec norms (2025–2026)

## Findings

### [1] MCP spec version lineage is 2024-11-05 → 2025-03-26 → 2025-06-18 → 2025-11-25 → 2026-07-28, and 2026-07-28 is the current "latest" stable revision (with a separate Draft channel).
- quote: "Version 2026-07-28 (latest) / Version 2025-11-25 / Version 2025-06-18 / Version 2025-03-26 / Version 2024-11-05 / Draft"
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/docs.json
- source_type: primary
- published: 2026-07-28 (version label); docs.json as fetched 2026-10-20
- confidence: high

### [2] Protocol revision 2026-07-28 makes MCP stateless: it removes the `initialize`/`notifications/initialized` handshake and the `Mcp-Session-Id` header; every request carries protocol version + client capabilities in `_meta`, version mismatch returns `UnsupportedProtocolVersionError` (-32022), and servers MUST implement a new `server/discover` RPC (clients MAY call it first or probe inline).
- quote: "Make MCP stateless: remove the `initialize`/`notifications/initialized` handshake. Every request now carries its protocol version and client capabilities in `_meta` (`io.modelcontextprotocol/protocolVersion`, `io.modelcontextprotocol/clientCapabilities`) ... Version mismatches return `UnsupportedProtocolVersionError`" ... "Add `server/discover`: servers MUST implement this RPC to advertise their supported protocol versions, capabilities, and identity."
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/changelog.mdx
- source_type: primary
- published: 2026-07-28
- confidence: high

### [3] Legacy lifecycle (2025-11-25 and earlier): `initialize` MUST be the first interaction; the client MUST send `protocolVersion` + capabilities + `clientInfo`, the server MUST answer with its own capabilities/`serverInfo`, the client MUST then send `notifications/initialized`, and on HTTP the client MUST send `MCP-Protocol-Version: <version>` on all subsequent requests; the 2026 spec calls these versions "legacy" and 2026-07-28+ "modern".
- quote: "The initialization phase **MUST** be the first interaction between client and server. ... After successful initialization, the client **MUST** send an `initialized` notification ... If using HTTP, the client **MUST** include the `MCP-Protocol-Version: <protocol-version>` HTTP header on all subsequent requests"
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2025-11-25/basic/lifecycle.mdx
- source_type: primary
- published: 2025-11-25
- confidence: high

### [4] Tool annotations (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`, `title`) are advisory hints only — defaults `readOnlyHint=false`, `destructiveHint=true`, `idempotentHint=false`, `openWorldHint=true`; `destructiveHint`/`idempotentHint` matter only when `readOnlyHint == false`; clients MUST treat annotations from untrusted servers as untrusted; the hints were introduced in revision 2025-03-26 (PR #185) and are unchanged in 2026-07-28.
- quote: "If true, the tool may perform destructive updates to its environment. If false, the tool performs only additive updates. (This property is meaningful only when `readOnlyHint == false`) Default: true" ... "Clients should never make tool use decisions based on ToolAnnotations received from untrusted servers." (changelog 2025-03-26: "Added comprehensive **tool annotations** ... whether it is read-only or destructive (PR #185)")
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/schema/2025-11-25/schema.json
- source_type: primary
- published: 2025-03-26 (origin), schema text as of 2025-11-25/2026-07-28
- confidence: high

### [5] `tools/list` MUST return `tools[]` with `name` + `inputSchema`; inputSchema MUST be a valid JSON Schema object (not null), defaults to JSON Schema 2020-12; for zero-parameter tools the recommended form is `{ "type": "object", "additionalProperties": false }`; tool names SHOULD be 1–128 chars, case-sensitive, limited to `[A-Za-z0-9_.-]`, unique per server (guidance added in 2025-11-25, SEP-986).
- quote: "**MUST** be a valid JSON Schema object (not `null`) - For tools with no parameters, use one of these valid approaches: - `{ \"type\": \"object\", \"additionalProperties\": false }` - **Recommended**" ... "Tool names **SHOULD** be between 1 and 128 characters in length (inclusive). Tool names **SHOULD** be considered case-sensitive."
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2025-11-25/server/tools.mdx
- source_type: primary
- published: 2025-11-25
- confidence: high

### [6] Structured tool output (`structuredContent`) was added in 2025-06-18 (PR #371); if a tool declares `outputSchema`, servers MUST return structured results conforming to it and clients SHOULD validate against it; for backward compatibility a tool returning structured content SHOULD also emit the serialized JSON in a `TextContent` block.
- quote: "If an output schema is provided: - Servers **MUST** provide structured results that conform to this schema. - Clients **SHOULD** validate structured results against this schema." ... "For backwards compatibility, a tool that returns structured content SHOULD also return the serialized JSON in a TextContent block."
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2025-11-25/server/tools.mdx
- source_type: primary
- published: 2025-06-18 (feature), text as of 2025-11-25
- confidence: high

### [7] The tools error contract splits two channels: tool execution failures (API failures, input validation, business logic) SHOULD be returned inside the result with `isError: true` so the LLM can self-correct, while unknown tool / malformed request / server faults are JSON-RPC protocol errors (e.g. -32602 Unknown tool); 2025-11-25 explicitly moved input-validation errors to the Tool Execution Errors channel (SEP-1303).
- quote: "**Tool Execution Errors**: Reported in tool results with `isError: true`: API failures, Input validation errors ... **Protocol Errors**: Standard JSON-RPC errors for issues like: Unknown tools, Malformed requests" ... "Clarify that input validation errors should be returned as Tool Execution Errors rather than Protocol Errors to enable model self-correction (SEP-1303)."
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2025-11-25/server/tools.mdx
- source_type: primary
- published: 2025-11-25
- confidence: high

### [8] Pagination is cursor-based and opaque: `tools/list`, `resources/list`, `resources/templates/list`, `prompts/list` accept `cursor` and return optional `nextCursor`; clients MUST NOT parse/modify/persist cursors across sessions, MUST NOT assume fixed page size, and invalid cursors SHOULD yield -32602.
- quote: "Pagination in MCP uses an opaque cursor-based approach ... Clients **MUST** treat cursors as opaque tokens: Don't make assumptions about cursor format ... Don't persist cursors across sessions. ... Invalid cursors **SHOULD** result in an error with code -32602 (Invalid params)."
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2025-11-25/server/utilities/pagination.mdx
- source_type: primary
- published: 2025-11-25
- confidence: high

### [9] Progress tracking is opt-in per request via `_meta.progressToken` (string|integer, MUST be unique across active requests); `notifications/progress` MUST carry monotonically increasing `progress` (MAY be float), MAY omit `total`, and MUST stop after completion; both parties SHOULD rate-limit progress flooding.
- quote: "Progress tokens **MUST** be a string or integer value ... **MUST** be unique across all active requests. ... The `progress` value **MUST** increase with each notification, even if the total is unknown. ... Progress notifications **MUST** stop after completion"
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2025-11-25/basic/utilities/progress.mdx
- source_type: primary
- published: 2025-11-25
- confidence: high

### [10] A compliant server exposing resources/prompts MUST declare the corresponding capability (`resources` with optional `subscribe`/`listChanged`, `prompts` with optional `listChanged`) during initialization; when the list changes and `listChanged` was declared, the server SHOULD send `notifications/*/list_changed`; resource content MUST include `uri`, and binary data MUST be base64-encoded with a valid MIME type.
- quote: "Servers that support resources **MUST** declare the `resources` capability" ... "Servers that support prompts **MUST** declare the `prompts` capability during initialization" ... "The image data **MUST** be base64-encoded and include a valid MIME type."
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2025-11-25/server/resources.mdx
- source_type: primary
- published: 2025-11-25 (prompts.mdx same version)
- confidence: high

### [11] In 2026-07-28 every result MUST carry `resultType` (`"complete"` or `"input_required"`; clients MUST treat an absent field as `"complete"` for older servers), `tools/list` results MUST include `ttlMs` + `cacheScope` (`CacheableResult`), servers SHOULD return tools in deterministic order for client/LLM prompt caching, and `inputSchema`/`outputSchema` were loosened to any JSON Schema 2020-12 keywords with `structuredContent` allowed to be any JSON value.
- quote: "All results now carry a required `resultType` field ... Clients **MUST** treat results from earlier-protocol servers that omit the field as `\"complete\"`" ... "Require `ttlMs` and `cacheScope` fields on results returned by `tools/list` ... Servers **SHOULD** return tools from `tools/list` in a deterministic order to enable client-side caching and improve LLM prompt cache hit rates."
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/changelog.mdx
- source_type: primary
- published: 2026-07-28
- confidence: high

### [12] 2026-07-28 deprecates Roots, Sampling and Logging (minimum 12-month deprecation window), reclassifies HTTP+SSE transport as Deprecated (migrate to Streamable HTTP), and moves experimental tasks out of core into extension `io.modelcontextprotocol/tasks` (polling `tasks/get`, mid-flight input via `tasks/update`).
- quote: "Deprecate the Roots, Sampling, and Logging features ... Suggested migrations: pass directories or files via tool parameters ... log to `stderr` (stdio) or use OpenTelemetry instead of Logging." ... "Move experimental tasks out of the core protocol and into an official extension (`io.modelcontextprotocol/tasks`)."
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/changelog.mdx
- source_type: primary
- published: 2026-07-28
- confidence: high
