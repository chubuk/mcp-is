# F2: Tool authoring best practices & LLM ergonomics

## Findings

### [1] Tool description quality is the single most important factor in tool-use performance; Anthropic recommends at least 3–4 sentences per tool covering what it does, when to use (and not use) it, what each parameter means, and caveats/limitations.
- quote: "Provide extremely detailed descriptions. This is by far the most important factor in tool performance... Aim for at least 3–4 sentences for each tool description, more if the tool is complex."
- url: https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools
- source_type: primary
- published: unknown (current as of 2026-10; page documents `input_examples`, `defer_loading`, tool search)
- confidence: high

### [2] Small, precise refinements to tool descriptions produce large measurable gains: Anthropic reports SWE-bench Verified SOTA for Claude Sonnet 3.5 after description refinements, and fixed a web-search bug (Claude appending "2025" to every query) purely by editing the tool description.
- quote: "Even small refinements to tool descriptions can yield dramatic improvements. Claude Sonnet 3.5 achieved state-of-the-art performance on the SWE-bench Verified evaluation after we made precise refinements to tool descriptions, dramatically reducing error rates and improving task completion."
- url: https://www.anthropic.com/engineering/writing-tools-for-agents
- source_type: primary
- published: 2025-09-11
- confidence: high

### [3] Tools should consolidate multi-step workflows rather than wrap raw API endpoints 1:1 — e.g. `schedule_event` instead of `list_users`+`list_events`+`create_event`, `search_logs` instead of `read_logs`, `get_customer_context` instead of separate id/transactions/notes getters.
- quote: "A common error we've observed is tools that merely wrap existing software functionality or API endpoints—whether or not the tools are appropriate for agents... consider implementing a schedule_event tool which finds availability and schedules an event."
- url: https://www.anthropic.com/engineering/writing-tools-for-agents
- source_type: primary
- published: 2025-09-11
- confidence: high

### [4] Namespacing tool names with service/resource prefixes (asana_search, asana_projects_search) delineates boundaries across many tools; prefix- vs suffix-based namespacing has non-trivial effects on tool-use evals and the winner varies by LLM, so the choice must be validated per model.
- quote: "We have found selecting between prefix- and suffix-based namespacing to have non-trivial effects on our tool-use evaluations. Effects vary by LLM and we encourage you to choose a naming scheme according to your own evaluations."
- url: https://www.anthropic.com/engineering/writing-tools-for-agents
- source_type: primary
- published: 2025-09-11
- confidence: high

### [5] LLM tool-selection accuracy degrades beyond 30–50 simultaneously available tools; a typical 5-server toolset consumes ~55k tokens of definitions, and Anthropic's tool search (regex/bm25 variants dated 2025-11-19, `defer_loading: true`) loads only the 3–5 needed tools, cutting definition tokens by >85% while keeping selection accuracy high across thousands of tools.
- quote: "Claude's ability to pick the right tool degrades once you exceed 30–50 available tools. Because tool search loads only a focused set of relevant tools on demand, selection accuracy stays high even across thousands of tools."
- url: https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool
- source_type: primary
- published: unknown (tool versions `tool_search_tool_{regex,bm25}_20251119`; docs current as of 2026-10)
- confidence: high

### [6] MCP 2026-07-28 spec: tool names SHOULD be 1–128 chars, case-sensitive, restricted to [A-Za-z0-9_.-], unique within one server; aggregating clients SHOULD disambiguate collisions by prefixing with a server identifier (serverInfo.name is NOT unique and must not be relied on).
- quote: "Tool names SHOULD be between 1 and 128 characters in length (inclusive)... The following SHOULD be the only allowed characters: uppercase and lowercase ASCII letters (A-Z, a-z), digits (0-9), underscore (_), hyphen (-), and dot (.)"
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/server/tools.mdx
- source_type: primary
- published: 2026-07-28 (protocol version)
- confidence: high

### [7] MCP error contract: tool execution errors (validation, business logic, API failures) MUST be returned as tool results with `isError: true` and actionable text for LLM self-correction; only protocol-level problems (unknown tool, malformed request) go to JSON-RPC errors, which models rarely recover from.
- quote: "Any errors that originate from the tool SHOULD be reported inside the result object, with isError set to true, not as an MCP protocol-level error... Clients SHOULD provide tool execution errors to language models to enable self-correction."
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/server/tools.mdx
- source_type: primary
- published: 2026-07-28 (protocol version)
- confidence: high

### [8] MCP result shape: structured data goes in `structuredContent` conforming to an optional `outputSchema` (validated by clients), and for backwards compatibility the same JSON SHOULD also be serialized into a TextContent block; response structure (JSON/Markdown/XML) has no universal winner and must be chosen by evaluation.
- quote: "For backwards compatibility, a tool that returns structured content SHOULD also return the serialized JSON in a TextContent block."
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/server/tools.mdx
- source_type: primary
- published: 2026-07-28 (protocol version)
- confidence: high

### [9] Response verbosity can be a tool parameter: Anthropic's `response_format` enum ("detailed" | "concise") lets the agent trade IDs needed for follow-up calls vs tokens — their Slack example costs 206 tokens detailed vs 72 concise (~1/3), while still exposing `thread_ts`/`user_id` in detailed mode for chained calls.
- quote: "You can enable both by exposing a simple response_format enum parameter in your tool, allowing your agent to control whether tools return 'concise' or 'detailed' responses... In this example, we use ~⅓ of the tokens with 'concise' tool responses."
- url: https://www.anthropic.com/engineering/writing-tools-for-agents
- source_type: primary
- published: 2025-09-11
- confidence: high

### [10] Large list results need pagination, range selection, filtering, and/or truncation with sensible defaults; Claude Code truncates tool responses at 25,000 tokens by default, and truncation/error payloads should instruct the agent toward narrower queries or filters instead of opaque codes or tracebacks.
- quote: "We suggest implementing some combination of pagination, range selection, filtering, and/or truncation with sensible default parameter values for any tool responses that could use up lots of context. For Claude Code, we restrict tool responses to 25,000 tokens by default."
- url: https://www.anthropic.com/engineering/writing-tools-for-agents
- source_type: primary
- published: 2025-09-11
- confidence: high

### [11] ID ergonomics: tools should return high-signal, semantically meaningful identifiers and avoid low-level technical ones (uuid, mime_type, 256px_image_url); Anthropic measured that resolving arbitrary alphanumeric UUIDs to interpretable names or even 0-indexed IDs significantly improves retrieval precision and reduces hallucinations, while parameters must be unambiguously named (`user_id`, not `user`).
- quote: "We've found that merely resolving arbitrary alphanumeric UUIDs to more semantically meaningful and interpretable language (or even a 0-indexed ID scheme) significantly improves Claude's precision in retrieval tasks by reducing hallucinations."
- url: https://www.anthropic.com/engineering/writing-tools-for-agents
- source_type: primary
- published: 2025-09-11
- confidence: high

### [12] For complex inputs, Claude's API supports an `input_examples` array of schema-validated example objects alongside descriptions; constrained parameters (statuses, currencies, sort orders) should be expressed as schema `enum`s rather than free-text strings (Google's Gemini function-calling docs use this pattern for `color_temp: enum[daylight, cool, warm]`).
- quote: "Prioritize descriptions, but consider using input_examples for complex tools. Clear descriptions are most important, but for tools with complex inputs, nested objects, or format-sensitive parameters, you can use the input_examples field to provide schema-validated examples."
- url: https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools
- source_type: primary
- published: unknown (current as of 2026-10)
- confidence: high

### [13] Server-level guidance exists in the protocol: `InitializeResult.instructions` is free-form natural-language guidance about the server and its tools that clients may inject into the system prompt, and tools/list SHOULD return tools in deterministic order so clients can cache the list and hit LLM prompt caches — both matter when a server exposes hundreds of tools.
- quote: "Natural-language guidance describing the server and its features. This can be used by clients to improve an LLM's understanding of available tools (e.g., by including it in a system prompt)... Deterministic ordering enables clients to reliably cache the tool list and improves LLM prompt cache hit rates when tools are included in model context."
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/schema.mdx
- source_type: primary
- published: 2026-07-28 (protocol version)
- confidence: high

### [14] MCP `ToolAnnotations` (`readOnlyHint` default false, `destructiveHint` default true, `idempotentHint` default false, `openWorldHint` default true) advertise side-effect semantics for confirmation UX, but are explicitly hints only — clients must not trust them from untrusted servers.
- quote: "NOTE: all properties in ToolAnnotations are hints. They are not guaranteed to provide a faithful description of tool behavior... Clients should never make tool use decisions based on ToolAnnotations received from untrusted servers."
- url: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/schema.mdx
- source_type: primary
- published: 2026-07-28 (protocol version)
- confidence: high
