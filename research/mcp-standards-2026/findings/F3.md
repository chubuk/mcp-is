# F3: Production MCP servers at scale

## Findings

### [1] GitHub consolidated many fine-grained CRUD tools into verb-family tools (`issue_read` / `issue_write` / `actions_list` / `projects_get`), keeping old names as silent deprecation aliases.
- quote: "The deprecation alias system allows us to maintain backward compatibility by silently resolving old tool names to their new canonical names. ... Example: If renaming `get_issue` to `issue_read`"
- url: https://raw.githubusercontent.com/github/github-mcp-server/main/docs/tool-renaming.md
- source_type: primary
- published: unknown (fetched 2026-10-20)
- confidence: high

### [2] GitHub's alias table shows the consolidation direction explicitly: `list_projects`+`list_project_items`+`list_project_fields` → `projects_list`, `get_*` → `*_get`, and all project mutations → `projects_write` (one write tool instead of add/delete/update variants).
- quote: "| `add_project_item` | `projects_write` | ... | `list_projects` | `projects_list` | ... | `update_project_item` | `projects_write` |"
- url: https://raw.githubusercontent.com/github/github-mcp-server/main/docs/tool-renaming.md
- source_type: primary
- published: unknown (fetched 2026-10-20)
- confidence: high

### [3] GitHub MCP Server partitions tools into named "toolsets" (repos, issues, actions, code_security, ...), each selectable via a URL path segment on the remote server, with a `/readonly` suffix to strip write tools from any toolset.
- quote: "Each toolset is provided as a distinct URL so you can mix and match to create the perfect combination of tools for your use-case. Add `/readonly` to the end of any URL to restrict the tools in the toolset to only those that enable read access."
- url: https://raw.githubusercontent.com/github/github-mcp-server/main/docs/remote-server.md
- source_type: primary
- published: unknown (fetched 2026-10-20)
- confidence: high

### [4] GitHub list tools paginate with explicit `page`/`perPage` parameters (default 30, max 100) and/or `cursor` where the API supports it; batch mutations are hard-capped (e.g. 50 items per call) instead of unbounded.
- quote: "`page`: Page number for pagination (default: 1) (number, optional) - `perPage`: Results per page for pagination (default: 30, max: 100) (number, optional) ... Limit: 50 items per call."
- url: https://raw.githubusercontent.com/github/github-mcp-server/main/README.md
- source_type: primary
- published: unknown (fetched 2026-10-20)
- confidence: high

### [5] GitHub returns tool results as compact DTOs projected from API responses (excluding API/node/hypermedia URLs), and exposes `outputSchema`/`structuredContent` only for negotiated protocol version `2026-07-28` or newer, keeping legacy text responses for older clients.
- quote: "Issue and comment data are projected from the API responses into compact DTOs, excluding API, node, and hypermedia URLs while retaining human links. ... The output schema and `structuredContent` are exposed only for a negotiated, SDK-supported protocol version `2026-07-28` or later."
- url: https://raw.githubusercontent.com/github/github-mcp-server/main/docs/typed-tool-schemas.md
- source_type: primary
- published: unknown (fetched 2026-10-20)
- confidence: high

### [6] GitHub splits errors into user-actionable failures (returned as failed tool calls: auth, rate limit, 404) vs developer errors (bubbling as Go errors), and stores API errors in context so middleware can monitor without logging PII.
- quote: "User-actionable errors (authentication failures, rate limits, 404s) should be returned as failed tool calls ... Developer errors (JSON marshaling failures, internal logic errors) should be returned as actual Go errors that bubble up through the MCP framework"
- url: https://raw.githubusercontent.com/github/github-mcp-server/main/docs/error-handling.md
- source_type: primary
- published: unknown (fetched 2026-10-20)
- confidence: high

### [7] GitHub hides tools the token cannot use for classic PATs (scope filtering from `X-OAuth-Scopes`), but for OAuth remote sessions it keeps all tools registered and requests scopes on demand via "scope challenges".
- quote: "Classic PAT (`ghp_`) | Filters tools at startup based on token scopes—tools requiring unavailable scopes are hidden | OAuth (remote server only) | Uses OAuth scope challenges—when a tool needs a scope you haven't granted, you're prompted to authorize it"
- url: https://raw.githubusercontent.com/github/github-mcp-server/main/docs/scope-filtering.md
- source_type: primary
- published: unknown (fetched 2026-10-20)
- confidence: high

### [8] Sentry MCP sets a hard tool-count budget for its public surface: target ~20 tools, never exceed 25, because clients cap total tool slots (Cursor caps 45 across all providers).
- quote: "Target ~20 publicly visible tools. Never exceed 25. AI agents have limited tool slots (Cursor caps at 45 total across all providers), so Sentry MCP cannot consume all available slots."
- url: https://raw.githubusercontent.com/getsentry/sentry-mcp/main/docs/contributing/adding-tools.md
- source_type: primary
- published: unknown (fetched 2026-10-20)
- confidence: high

### [9] Sentry keeps the long tail of tools in a searchable catalog behind two meta-tools (`search_sentry_tools` + `execute_sentry_tool`), and only high-frequency foundational tools go into `TOP_LEVEL_TOOL_NAMES` / `tools/list`.
- quote: "Catalog by default — Most tools are searchable/executable through `search_sentry_tools` + `execute_sentry_tool` automatically. ... Add only high-frequency, foundational tools to `TOP_LEVEL_TOOL_NAMES`. Leave long-tail tools out of the direct surface unless there is a clear reason they need to be visible without discovery."
- url: https://raw.githubusercontent.com/getsentry/sentry-mcp/main/docs/contributing/adding-tools.md
- source_type: primary
- published: unknown (fetched 2026-10-20)
- confidence: high

### [10] Sentry MCP scopes multi-tenant sessions in the URL path (`https://mcp.sentry.dev/mcp/{organizationSlug}/{projectSlug}`), and when scoped, defaults the org/project and hides unnecessary discovery tools; tool subsets are further controlled with `?skills=` / `?disable-skills=`.
- quote: "https://mcp.sentry.dev/mcp/{organizationSlug} — scoped to one organization ... When scoped, tools automatically default to the constrained org/project and unnecessary discovery tools are hidden. Scoping to a project is recommended when possible."
- url: https://docs.sentry.io/product/sentry-mcp/
- source_type: primary
- published: unknown (fetched 2026-10-20)
- confidence: high

### [11] Sentry mandates explicit safety annotations on every tool (`readOnlyHint`, `destructiveHint`, `openWorldHint`, optional `idempotentHint`) at compile time, because filters and confirmation gates depend on them.
- quote: "**REQUIRED**: Every tool must declare `readOnlyHint`, `destructiveHint`, and `openWorldHint` explicitly (each `true` or `false`, never omitted). This is enforced at compile time ... because filters and confirmation gates depend on these hints; an absent hint is a silent gap."
- url: https://raw.githubusercontent.com/getsentry/sentry-mcp/main/docs/contributing/adding-tools.md
- source_type: primary
- published: unknown (fetched 2026-10-20)
- confidence: high

### [12] Sentry's response policy treats tool output as product UX: stable markdown sections with follow-up tool hints, `structuredContent` as source of truth with `content` as an equivalent compatibility view, no raw upstream API JSON, no placeholder noise, capped lists with "N omitted".
- quote: "Tool responses are product UX for agents and users. ... `structuredContent` is the source of truth when present. `content` text is a compatibility view of that same answer. Never put unique product data in only one side."
- url: https://raw.githubusercontent.com/getsentry/sentry-mcp/main/docs/contributing/tool-responses.md
- source_type: primary
- published: unknown (fetched 2026-10-20)
- confidence: high

### [13] Anthropic: "more tools don't always lead to better outcomes"; tools that merely wrap existing APIs are a common error, and namespacing by service and by resource (`asana_search` vs `asana_projects_search`) measurably affects tool selection — prefix vs suffix choice should be decided by your own evals.
- quote: "More tools don't always lead to better outcomes. A common error we've observed is tools that merely wrap existing software functionality or API endpoints—whether or not the tools are appropriate for agents. ... Namespacing (grouping related tools under common prefixes) can help delineate boundaries between lots of tools ... We have found selecting between prefix- and suffix-based namespacing to have non-trivial effects on our tool-use evaluations."
- url: https://www.anthropic.com/engineering/writing-tools-for-agents
- source_type: primary
- published: 2025-09-11
- confidence: high

### [14] Notion's hosted MCP exposes a curated ~24-tool surface with a `notion-` prefix (search/ai-search/fetch, create-pages, update-page, query-data-sources, ...), lets workspace admins pick a per-connection tool subset, and soft-degrades unavailable plan features with a `notices` array instead of failing the call.
- quote: "Workspace-owned MCP connections list only the tools an admin selected for the connection, from this set: `notion-search`, `notion-ai-search`, `notion-fetch`, ... `notion-query-multiple-data-sources`. ... A filter or sort that the workspace's plan doesn't include doesn't fail the call. Notion drops the unavailable options ... and adds a `notices` array to the response."
- url: https://developers.notion.com/guides/mcp/mcp-supported-tools.md
- source_type: primary
- published: unknown (fetched 2026-10-20)
- confidence: high

### [15] Notion documents deprecated-but-still-callable tools explicitly (`notion-ai-search` stays callable by name after removal from `tools/list`) so clients with cached tool lists keep working, and gates capability differences in tool descriptions themselves.
- quote: "In sessions that list one search tool, `notion-ai-search` (`ai-search` for OpenAI clients) no longer appears in `tools/list`. It stays callable by name, so a client with a cached tool list keeps working, and it behaves as before."
- url: https://developers.notion.com/guides/mcp/mcp-supported-tools.md
- source_type: primary
- published: unknown (fetched 2026-10-20)
- confidence: high
