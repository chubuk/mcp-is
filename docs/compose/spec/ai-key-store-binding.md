# AI Key → Store Binding & Connection Naming

## Report

**What was built** — Каждый ИИ-ключ теперь жёстко привязан к одному магазину InSales: создание без `shop_id` (и без магазинов в аккаунте) отклоняется, редактор не сохранит легаси-ключ без привязки, владение проверяется на всех операциях. Непривязанные ключи fail-closed: data-инструменты возвращают модели actionable-ошибку с инструкцией привязки вместо молчаливого фолбэка на дефолт-магазин. Идентификация соединения: атрибут `connection_name` (алиас, `a-z0-9-`, уникален в аккаунте, авто-суффикс при коллизии, partial unique index в БД), персональные instructions через `OnAfterInitialize` (алиас + магазин + правило «не угадывай»), инструмент `store_info` как ground truth, конфиг-сниппеты с алиасом в кабинете и на странице установки (с рабочей кнопкой «Скачать файл»). Плюс квоты `MAX_SHOPS_PER_USER`/`MAX_AI_KEYS_PER_USER` (дефолт 20, app-install вне квот) и перевыпуск ключа (`POST /api/ai-keys/{id}/rotate`) как штатный способ восстановления потерянного секрета.

**Verification** — `make lint` PASS (0 issues); `go vet ./...` PASS; `go test ./...` PASS (12 пакетов); `go test -tags integration ./internal/storage/` PASS (локальный Postgres, включая новые тесты unique index / NULL-handling / collision suffix); ручной браузерный прогон (Playwright + локальный стек: Postgres + сервер + nginx-прокси) PASS: блокировка создания без магазинов, форма с выбором магазина и предзаполненным алиасом, карточка выдачи (ключ один раз + алиас + сниппет + скачивание), бейдж «не привязан», принудительная привязка при сохранении легаси-ключа (коллизия → `romashka-2`), кнопка перевыпуска, страница onboarding с сниппетом/алиасом/скачиванием. Независимое ревью: REQUEST-CHANGES (1 major — unique index) → фикс → APPROVE.

**Journey log** — 1) Critic-ревью плана до кода поймало 2 major (merge-patch PUT ломал togglePDN; инвариант уникальности недостижим для легаси-строк) — правки в спеке избавили от багов в коде. 2) Субагентная реализация T1 застряла на двусмысленной сигнатуре — переход на гибрид (спека + прямая реализация + одно ревью) ускорил остальные 10 задач. 3) HTML `pattern="[a-z0-9-]"` невалиден в v-flag regex-движках, а в JS-строке `\-` схлопывается в `-` — нашёлось только живым браузером. 4) Приложенный авто-суффикс не заменяет DB unique index — ревью поймало TOCTOU. 5) `schema.sql` в проде применяет init БД, а не миграционный раннер — для локального теста БД его нужно накатывать вручную.

## [S1] Problem

Аккаунт mcp-is может держать несколько ключей магазинов InSales и несколько ИИ-ключей (MCP-токенов). Сегодня ручные ИИ-ключи создаются без привязки к магазину: `ai_keys.shop_id` остаётся NULL, а `core.AccountManager.GetClient` молча берёт магазин по умолчанию (`shopRepo.GetDefault`). Модель не может узнать, к какому магазину подключена, — это ведёт к записи данных не в тот магазин.

Следствия: (1) создать ИИ-ключ можно даже при нуле магазинов; (2) у существующих непривязанных ключей нет редактора привязки; (3) имя соединения в конфиг-сниппетах (`{{KEY_NAME}}` = slug от названия ключа) никак не связано с магазином; (4) instructions сервера статические и одинаковы для всех ключей.

## [S2] Design

### [S2.1] Обязательная привязка к магазину

- Один ИИ-ключ → ровно один магазин (`ai_keys.shop_id`, FK `shops(id)` уже существует). Колонка остаётся NULLable только как состояние «не привязан» для легаси-ключей.
- `POST /api/ai-keys`: `shop_id` обязателен; должен ссылаться на магазин текущего пользователя, иначе 400. Если у аккаунта нет ни одного магазина — 400 с сообщением «Сначала добавьте магазин» (в UI кнопка создания ИИ-ключа скрыта/заблокирована с подсказкой).
- `PUT /api/ai-keys/{id}` — merge-patch (`name`, `pdn_enabled`, `connection_name`, `shop_id`): для уже привязанного ключа `shop_id` опционален (частичные апдейты вроде togglePDN продолжают работать); для **непривязанного** ключа `shop_id` обязателен в каждом запросе — легаси-ключ нельзя сохранить/изменить без привязки. Если `shop_id` передан — должен принадлежать пользователю.
- Владение: `Update`/`Delete` должны проверять `key.user_id == ctx user` (сейчас любой авторизованный пользователь может править/удалять чужой ключ по id) — исправляется в тех же хендлерах.
- `shop_id` в ответах List/Create/Update + имя магазина (JOIN) и признак привязки; колонка «Магазин» в таблице UI, у непривязанных — бейдж «не привязан».

### [S2.2] Легаси-ключи без привязки: отказ вместо дефолт-магазина

- `AccountManager.GetClient` больше не делает фолбэк на `GetDefault(userID)`: пустой `shop_id` → sentinel-ошибка `ErrKeyNotBound`.
- Все data-инструменты возвращают tool error (`isError`) с actionable-текстом для модели (best practice спеки MCP: tool execution errors — модель-обрабатываемые, в отличие от протокольных): «AI-ключ не привязан к магазину. Попросите владельца привязать ключ к магазину в личном кабинете → AI-ключи и повторите запрос.» Данные не отдаются до привязки (fail-closed: исключаем запись не в тот магазин).
- Удаление магазина (`ON DELETE SET NULL`) даёт то же состояние «не привязан» → то же сообщение.

### [S2.3] Именование и идентификация соединения

- `connection_name` — новый атрибут ИИ-ключа (`ai_keys.connection_name TEXT`): алиас соединения, который пользователь видит в конфиге клиента и о котором говорит модель.
  - Дефолт: `core.Slugify(shop.Name)` (уже есть в кодовой базе); редактируемый при создании/редактировании.
  - Валидация: `^[a-z0-9-]{1,64}$`, уникален в пределах аккаунта. Без `_`, `.`, `/` — пересечение требований SEP-986, текущего спека (A-Za-z0-9_-. до 128) и парсеров типа Cloudflare (одиночный `_` ломает namespacing; `mcp__<alias>__<tool>` — alias не должен содержать `_`).
  - Уникальность — только среди **сохранённых** значений (partial unique index по (user_id, connection_name) для непустых); при коллизии авто-суффикс `-2`, `-3`. Дефолт, вычисленный при чтении для легаси-NULL строк, уникальность не проверяется (это display-only fallback).
  - Хранение/чтение: если у легаси-строки пусто — вычисляем дефолт при чтении (stored → Slugify(shop.Name) → "mcp-is"); сохраняется при первом create/edit. Автоключи app-install («InSales: <host>») также получают `connection_name` при создании (slug от магазина).
- `serverInfo.name` остаётся константой `"mcp-is"` — спека запрещает использовать serverInfo для логики/безопасности.
- Instructions — per-connection через `Hooks.OnAfterInitialize` (mcp-go v0.56.0: мутируем `InitializeResult.Instructions` из ctx). В первые 512 символов: `Connection: <connection_name>`, `Store: "<name>" (<domain>)`, «все инструменты работают только с этим магазином; перед записью вызовите `store_info`». Для непривязанного ключа — уведомление «ключ не привязан, настройте привязку» (строго информационное, non-load-bearing: основной канал отказа — S2.2). Имя/домен магазина и `connection_name` кладёт в контекст middleware (JOIN shops в запросе аутентификации) — без отдельного запроса при initialize. Примечание: `server/discover` (ревизия 2026-07-28) mcp-go не реализует — отдаём только InitializeResult; клиенты обеих эпох это принимают (legacy-handshake).
- Новый инструмент `store_info` (core-поверхность, без вызова InSales): `{connection_name, key_name, bound, store: {name, shop_url, id}, read_only}`. Работает и для непривязанных ключей (`bound:false` + текст из S2.2) — ground truth для модели.
- Конфиг-сниппеты на выдаче ключа: подстановка `{{KEY_NAME}}` в шаблонах `mcp_client_types` берёт `connection_name` (не slugify(name)); рядом — название магазина. Правило алиаса показано в UI.

### [S2.4] UI

- Форма создания: выбор магазина (обязательно), `connection_name` (предзаполнен slug магазина, редактируем), название, ПДн. Без магазинов — создание недоступно с подсказкой «Сначала добавьте магазин».
- Форма редактирования: те же поля привязки; сохранение без магазина невозможно. Для непривязанного ключа — предупреждение «ключ не привязан, ИИ-запросы отклоняются».
- Таблица: колонка «Магазин», бейдж «не привязан».

### [S2.5] Лимиты магазинов и ИИ-ключей

- Две независимые переменные окружения (`.env`, чтение через `config.getEnvInt`): `MAX_SHOPS_PER_USER` (дефолт 20) и `MAX_AI_KEYS_PER_USER` (дефолт 20). Отсутствие/мусор в значении → дефолт 20.
- Проверка при ручном создании: `POST /api/shops` — при `count(shops) >= лимита` → 403 с сообщением «Достигнут лимит магазинов (N)»; `POST /api/ai-keys` — аналогично по ИИ-ключам. Лимиты считаются по `user_id`.
- Автопровижининг app-install (установка приложения InSales создаёт магазин и ключ «InSales: <host>») квотами не ограничивается — иначе ломается onboarding в InSales. Квоты действуют на ручные создания в личном кабинете.

### [S2.6] Выдача и перевыпуск секрета ключа

- Raw-ключ показывается ровно один раз (create-ответ; ответ install/link при установке приложения) — с кнопками копирования и конфиг-сниппетом. Так и сейчас; правило остаётся: хранится только hash, повторный показ не предлагается (паттерн GitHub/Stripe, OWASP Secrets Management: «never be logged», least privilege).
- Потерянный ключ восстанавливается **перевыпуском** (ротацией), а не повторным показом: `POST /api/ai-keys/{id}/rotate` (владелец обязателен) генерирует новый raw-ключ и заменяет `key_hash`; старый секрет перестаёт работать немедленно; имя, привязка к магазину, `connection_name`, ПДн сохраняются. Новый raw возвращается один раз — с тем же UI «скопируйте сейчас» и конфиг-сниппетом.
- UI: кнопка «Перевыпустить ключ» в редакторе ИИ-ключа с подтверждением «старый ключ перестанет работать у AI-агентов». Для app-install ключей («InSales: <host>») — та же кнопка: при пропуске одноразового показа ключ перевыпускается из редактора.
- Страница установки/onboarding (`auth.js` showKey) показывает не только ключ и URL, но и **примеры конфига подключения** (селектор типа клиента из `mcp_client_types`, алиас = `connection_name`) и **рабочую кнопку «Скачать файл»** — тот же механизм, что в кабинете (`Blob` + `a.download = file_name`, чисто клиентский). Ответы, выдающие raw-ключ (`ExchangeCode`, `LinkPending`), дополнительно возвращают `connection_name`.

## [S3] Out of Scope

- Ключ на несколько магазинов / параметр store в инструментах.
- `server/discover` и `InputRequiredResult`/elicitation (ревизия 2026-07-28) — SDK mcp-go v0.56.0 их не поддерживает.
- Смена `serverInfo.name`, переименование автоключей app-install («InSales: <host>») — они уже привязаны.
- Версионирование пакета / релиз deb (по правилам проекта — только при смене версии; здесь версия не меняется).
