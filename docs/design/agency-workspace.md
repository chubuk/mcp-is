# Дизайн-нот: agency/workspace для SaaS-модели агентств

Статус: **проработка под будущее решение**, код не меняется. Цель — зафиксировать
миграцию заранее, чтобы переход «маркетплейс → SaaS для агентств» не был болезненным.

## Контекст

Сейчас модель данных плоская: `ai_keys(user_id, shop_id)` — ключ принадлежит
пользователю и (опционально) одному магазину (`schema.sql:48-62`). Сценарий
«агентство обслуживает клиентов» держится на AI-ключах клиентов и нашем хостинге.
Для SaaS с личным кабинетом агентства понадобится уровень agency/workspace:
несколько магазинов, роли внутри агентства, биллинг per-agency, изоляция данных.

## Целевая модель

```
agencies (id, name, billing_status, billing_until, created_at)
   └─ shops.agency_id      (nullable FK → agencies; NULL = «личный» магазин)
   └─ users.agency_id      (nullable FK → agencies) + users.agency_role (owner|manager|member)
   └─ ai_keys.agency_id    (nullable FK → agencies; ключ выдаётся в контексте агентства)
```

- `NULL agency_id` — обратная совместимость: текущие пользователи/магазины остаются «личными».
- `workspace` = agency_id в контексте запроса (аналог `shop_id` в `auth.ShopIDKey`).

## Что менять в коде (когда продукт решит)

1. **Схема (3 места, правило проекта)**: `schema.sql`, `migrations.sql`, `migrate.go` —
   таблица `agencies` + `agency_id` в `users`/`shops`/`ai_keys` + индексы. Прогнать
   `scripts/check-schema.sh`.
2. **Скоупинг клиента**: `internal/core/manager.go` `GetClient` — проверка
   «магазин принадлежит agency контекста» наравне с текущей проверкой
   `shop.UserID != userID`. Точка расширения — уже единая (choke point).
3. **Контекст**: `auth` middleware — новый `AgencyIDKey`; извлечение из JWT/API-ключа.
4. **Биллинг**: `CheckBilling` сейчас per-shop (`shops.billing_*`); для агентств —
   per-agency (`agencies.billing_*`) с приоритетом agency-тарифа над shop.
5. **UI**: раздел «Агентство» (участники, роли, магазины, подписка) поверх SPA в
   `web/static/`; текущий список магазинов фильтруется по agency.
6. **Аудит/ПДн**: `audit_log`/`pdn_access_log` — добавить `agency_id` для выборок
   по агентству (колонки уже текстовые, миграция безболезненная).

## Порядок миграции

1. `agencies` + nullable-колонки (без логики) — один релиз, нулевой риск.
2. Скоупинг GetClient + контекст — второй релиз (за фича-флагом не нужно: NULL = прежнее поведение).
3. Биллинг per-agency + UI — третий релиз, когда появится тариф.

## Осознанные ограничения текущего состояния

- Пока agency нет, «агентство» = обычный пользователь с AI-ключами клиентов
  (документировано в License FAQ README: работа через наш хостинг — без нарушения).
- Миграция `ai_keys` не требуется до шага 2 — существующие ключи продолжают работать.
