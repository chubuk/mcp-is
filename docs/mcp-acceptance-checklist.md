# Чеклист приёмки MCP-сервера

Порядок проверок при подключении нового MCP-сервера. Методика — по практике Гермеса
(skiлл systematic-debugging + reference native-mcp.md, уровни 0–7), дополнена уроками
инцидента mcp-is/testshop (2026-11-02). Сервер принимается, если пройдены все уровни;
каждый следующий уровень запускается только после успеха предыдущего.

## Два правила (главные)

1. **Клиент не патчится, пока серверный баг не доказан.** Ошибка валидации на клиенте
   и ошибка данных на сервере выглядят одинаково; различает их probe по сырому
   протоколу (curl/JSON-RPC), а не повторный вызов через клиент.
2. **Контрпример обязателен.** Каждая проверка включает действие, которое при
   исправной системе обязано НЕ сработать (запись с заведомо неверным именем поля,
   обращение к несуществующему id). Иначе «всё работает» неотличимо от «всё молча
   игнорируется».

## Уровни проверки (от дешёвого к дорогому)

| Уровень | Что проверяем | Признаки успеха |
|---|---|---|
| 0. Конфиг и секреты | `${VAR}` в конфиге, значение в `.env` | секреты не попадают в вывод/логи/чат |
| 1. Транспорт | DNS/TLS/порт | 401 (креды) ≠ 200 (схема); таймауты настроены |
| 2. Handshake | `initialize` → `mcp-session-id` → `notifications/initialized` | сессия продолжается по заголовку |
| 3. Discovery | `tools/list` строгими моделями | валидный JSON Schema (без `items:true` и др. boolean-подсхем); счётчик инструментов совпадает с ожиданиями; видно, какой срез отдаётся (core vs all) |
| 4. Чтение | один инструмент с известным ответом | данные совпадают с источником; типы аргументов (int vs str) не теряются |
| 5. Запись | запись с контрольным полем + read-back | неверное поле не создаёт эффекта (`updated_at` не сдвинулся); подтверждение — перечитыванием, не текстом «успех» |
| 6. Деградация | 503 и retry, пауза после серии ошибок, таймауты | ошибки видны агенту actionable-текстом; есть backoff/повтор |
| 7. Независимая сверка | второй канал (витрина, прямой HTTP, админка) | состояние совпадает — кеш исключён |

## Дополнения по итогам инцидента mcp-is (эхо-затирание)

- **Не принимать сообщение об успехе за доказательство** — всегда перечитывать
  состояние обратно (read-back), желательно другим инструментом/каналом.
- **Не «исправлять» токены и идентификаторы**, не выдавать правдоподобный вывод
  за полученный.
- **Эхо-тест**: взять полный ответ GET-инструмента и отправить его же как апдейт —
  данные должны остаться нетронутыми (пустые значения не должны затирать поля).
- **Ноль ≠ пустота**: числовые `0`/`false` — легитимная запись (остаток 0, скидка 0);
  «пустые» значения — только отдельным явным механизмом (например `clear_fields`).
- **Пагинация проверяется отдельно**: что значит `total`, как API ведёт себя на
  маленьких `per_page`, есть ли клампы/эмуляция.
- **Семантику пустых значений** (присутствующий ключ с пустым значением = запись
  пустоты?) фиксировать тестом, а не доводом — у InSales/Rails это поведение
  подтверждено практикой.
- **Скрытые состояния сущностей** (архив/корзина/скрытость) — смотреть через
  отображаемые поля ответа; если маппинг их не отдаёт — диагностировать по
  «до/после» снимкам и второму каналу.

## Памятка по mcp-is (частные случаи)

- Core surface (`MCP_TOOLS_MODE=core`, по умолчанию) показывает ~30 инструментов;
  остальные вызываются через `call_insales_tool` — это не баг discovery.
- `total` в конверте `{items, total}` = размер выдачи, не каталога.
- Ответы `/mcp` всегда `Cache-Control: no-store`.
